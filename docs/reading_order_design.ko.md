# 읽기 순서: 컨테이너, 애매함 감지, 판단 위임

[English](reading_order_design.md)

상태: 합의된 설계이며 단계별로 구현합니다([계획](#계획) 참고). 차세대 엔진
`rewrite/`에 적용하고, 이미 배포된 0.1.x 변환기는 지금 동작을 유지합니다.

## 문제

rewrite는 슬라이드의 도형을 펼친 뒤 재귀 XY-cut으로 순서를 정합니다
(`rewrite/src/pptx2markdown/reading_order.py`). 그룹은 절대 좌표 상자로
펼쳐지고, 글자 없는 테두리는 장식으로 버려지며, 자를 틈이 없는 영역은 좌표순
정렬로 떨어집니다. 그래서 세 가지 실패가 생깁니다.

1. **슬라이드를 덮는 배경**(그림, 또는 워터마크가 든 텍스트 상자)이 모든 영역과
   겹쳐 틈이 사라지고, 슬라이드 전체가 좌표순으로 정렬되어 나란한 카드의 줄이
   섞입니다.
2. **항상 열을 먼저 자릅니다.** 트랙 사이 가로 틈이 넓은 다이어그램에서도,
   화살표가 빠지며 생긴 좁은 세로 틈이 이겨 트랙마다 오른쪽 절반이 바닥글 뒤에
   읽힙니다.
3. **그룹과 테두리를 무시합니다.** 카드를 카드로 만드는 테두리를 버리고, 그룹
   안 도형이 바깥 도형과 섞이며, 1px 허용치를 넘게 겹친 상자가 열 사이 틈을
   막습니다.

## 근거

실제 덱(LibreOffice로 렌더링해 변환 순서와 비교):

| 덱 / 슬라이드 | 배치 | 현재 rewrite |
| --- | --- | --- |
| `brutalist_ai_newspaper_2026.pptx` 2 | 신문형 지면, 한 줄마다 텍스트 상자, 숫자와 단위 상자 겹침 | 카드가 줄 단위로 섞이고 III번 기사가 바닥글 뒤로 |
| `kubernetes_blueprint_2026.pptx` 5 | 화살표로 이은 가로 트랙 3개 | 트랙마다 오른쪽 절반이 바닥글 뒤로 |
| `glassmorphism_demo.pptx` 4 | 슬라이드를 덮는 그림 위 4 × 3 카드 | 슬라이드 전체가 좌표순 정렬 |
| `swiss_grid_systems.pptx` 7 | 깔끔한 3열 | 정상(대조군) |

코퍼스에서 텍스트 블록이 겹치거나 포함된 슬라이드는 94개 덱의 499장, 텍스트
도형 2개 이상을 담은 그룹이 있는 슬라이드는 43개 덱의 195장(중첩 그룹 45장)입니다.

`benchmarks/reading_order.py`는 기대 순서("이 문구들이 이 순서로, 다른 그룹
문구가 끼지 않고 나와야 한다")를 명시한 합성 케이스 11개를 만듭니다. 실제 덱의
XML 순서는 편집 이력을 따르므로 도형 저장 순서는 섞어 둡니다. 이 작업 전
기준선:

| 케이스 | rewrite | MarkItDown | anydoc |
| --- | :---: | :---: | :---: |
| 슬라이드를 덮는 그림 위 카드 격자 | ❌ | ❌ | ❌ |
| 워터마크가 든 전체 크기 텍스트 상자 위 2열 | ❌ | ❌ | ❌ |
| 다이어그램 트랙 2개, 열 사이 좁은 틈 | ❌ | ❌ | ❌ |
| 행이 어긋난 그룹 카드 | ❌ | ✅ | ❌ |
| 상자가 0.3인치 겹치는 2열 | ❌ | ❌ | ❌ |
| 숫자 상자와 단위 상자가 겹친 KPI 카드 | ✅ | ❌ | ❌ |
| 축 위아래를 번갈아 오가는 타임라인 | ✅ | ❌ | ❌ |
| 그림 위 콜아웃 + 아래 캡션 | ✅ | ✅ | ❌ |
| 그룹 안 그룹 사이드바 + 본문 그룹 | ✅ | ✅ | ✅ |
| 라벨을 가진 도형 안의 텍스트 상자 | ✅ | ❌ | ❌ |
| 대조군: 깔끔한 3열 | ✅ | ❌ | ❌ |
| **통과** | **6/11** | **3/11** | **1/11** |

anydoc은 도형을 XML 순서대로 읽습니다(저장 순서를 섞기 전 10/11, 섞은 뒤
1/11). MarkItDown이 그룹 카드를 통과하는 것은 그룹을 한 단위로 읽기 때문입니다.

## 결정

### 컨테이너 방식을 기본으로, 레시피로 끌 수 있게

읽기 순서는 취향이 아니라 정확성의 문제입니다. 한 카드의 줄이 다른 카드에
섞이면 그것으로 만든 모든 청크가 오염되고, 아무도 모르는 옵션은 아무도 보호하지
못합니다. rewrite는 아직 출시 전이라 기본값을 바꿔도 깨질 사용자가 없습니다.

| 부분 | 확신도 | 적용 방식 |
| --- | --- | --- |
| 슬라이드 90% 이상을 덮는 배경을 틈 계산에서 제외 | 높음: 배경은 읽기 단위가 아님 | 기본값, 스위치 없음 |
| 텍스트를 완전히 감싸는 테두리·그룹을 한 단위로 읽기 | 높음: 화면에 보이는 구조 | 기본값, 레시피로 끌 수 있음 |
| 정렬된 격자는 행 우선, 훨씬 넓은 틈부터 자르기 | 중간: 열 단위로 읽어야 하는 격자도 있음 | 기본값, 레시피로 변경 가능, 검토 항목으로 표시 |

스위치는 CLI 옵션이 아니라 레시피 설정(예: `"reading_order": "containers"` 또는
`"xycut"`)입니다. 레시피는 슬라이드 하나만 겨냥할 수 있고, 다른 변환 설정과
같은 자리에 있으며, 검토 답과 에이전트가 만들어 내는 결과이기 때문입니다.

어떤 부분을 기본값으로 삼는 조건은, 순서가 바뀐 코퍼스 슬라이드를 렌더링과
대조했을 때 나아졌고 나빠진 경우가 사실상 없는 것입니다. 일부 배치를 나쁘게
만드는 부분은 스위치 뒤(기본 꺼짐)로 내보냅니다.

### 언제나 맞는 기하학 규칙은 없다

읽기 순서는 작성자의 의도인데, PPTX에는 위치, 크기, 그룹, 편집 이력 순서만
저장되므로 같은 배치가 다른 순서를 뜻할 수 있습니다. 컨테이너 방식도 두 열에
걸친 강조 상자, 우연히 다른 도형을 감싸는 큰 텍스트 상자, 행 단위로 읽어야 하는
"도입 전 / 도입 후" 비교, 무관한 텍스트가 올라간 반쪽 사진 같은 경우에는
틀립니다. 그래서 목표는 다음과 같습니다.

1. 코퍼스 근거로 고른, 가장 자주 맞는 기본값
2. 그 기본값이 틀릴 수 있는 곳의 감지
3. 그곳만 사람이나 모델에게 맡기고, 선택은 레시피로 저장해 결정론적으로 재현

## XML로 애매함 감지하기

모든 신호는 렌더링 없이 도형 상자로 계산합니다.

| 신호 | 의미 | 대표 사례 |
| --- | --- | --- |
| 두 방향 모두 잘림 | 같은 영역을 세로·가로로 모두 자를 수 있고, 틈 폭이 비슷하며(0.5~2배), 두 순서가 다름 | 카드 격자, 다이어그램 트랙 |
| 자를 틈 없음 | 텍스트 도형 3개 이상인 영역에 틈이 없어 좌표순 정렬로 떨어짐 | 신문형 지면, 남아 있는 배경 |
| 부분 겹침 | 포함이 아닌 겹침, 특히 선택한 자르기 선을 가로지르는 경우 | 겹치는 열, 숫자 + 단위 |
| 경계를 넘는 컨테이너 | 테두리나 그룹이 상위 영역을 자른 열 경계에 걸침 | 두 열을 감싼 강조 상자 |
| 아슬아슬한 틈 | 가르는 틈이 허용치에서 몇 px 이내 | 거의 붙은 상자 |

앞의 두 신호는 XY-cut 자체에서 나옵니다. 선택지가 있었던 지점을 기록하면
됩니다. XML 순서는 대부분 편집 이력이므로 신호로 쓰지 않지만, 후보 순서 중
하나가 XML 순서와 같으면 동점 처리 근거로 씁니다.

표시된 슬라이드는 이유와 순서 후보 2~3개(행 우선, 열 우선, XML 순서)를 바로
쓸 수 있는 레시피 규칙으로 담은 `review()` 항목이 됩니다. 표시된 슬라이드만
LibreOffice로 로컬 렌더링해 후보와 함께 비전 모델에 보여 주고, 선택은
`{"target": "slide[4]", "reading_order": "rows"}`나 블록 id 순서를 직접 적은
`{"target": "slide[4]", "order": ["s4.b3", "s4.b1", ...]}` 같은 레시피 규칙이
됩니다.

감지할 수 없는 것: 기하학적으로 깔끔한데 의도한 순서가 뻔한 순서와 다른 배치.
이를 잡으려면 모든 슬라이드를 렌더링해 판단해야 하므로, 비용이 드는 명시적
옵션으로 제공할 수 있습니다.

## 검증

- `benchmarks/reading_order.py`에서 이 설계가 다루는 케이스는 모두 통과해야
  합니다(겹치는 열은 별도의 허용치 조정이 필요합니다).
- 어떤 부분을 기본값으로 삼기 전에 순서가 바뀐 코퍼스 슬라이드를 뽑아 렌더링과
  대조합니다.
- 애매함 감지: 실패하는 벤치마크 케이스와 이미 확인한 실제 실패 슬라이드는 모두
  표시돼야 하고(재현율), 표시되는 코퍼스 슬라이드 비율은 한 자릿수 %여야 하며
  (비용), 표시된 슬라이드 일부를 눈으로 확인합니다(정밀도).
- legacy parity의 순서 점수는 달라질 것이며, 바뀐 슬라이드를 검토한 뒤에만
  기준선을 갱신합니다.

## 결과 (1~3단계)

벤치마크: rewrite 6/11 → **9/11**(MarkItDown 3/11, anydoc 1/11). 아직 실패하는 둘
중 다이어그램 트랙은 표시되며 후보 "rows first"가 정답이고, 겹치는 열은 부분 겹침
신호와 허용치 조정이 필요합니다.

코퍼스(슬라이드 2,786장): XY-cut만 쓸 때와 비교해 171장의 텍스트 순서가 바뀌었습니다.
렌더링과 대조하면 거의 모두 개선입니다. 카드 격자, KPI 타일, 신문 기사, 다이어그램
패널이 단위로 읽히고, 쿠버네티스 트랙은 트랙 단위로 읽힙니다. 남은 악화 사례(맨
끝으로 간 머리 띠 날짜, 타원 속 번호)는 모두 검토 대상으로 표시됩니다. 다른 블록이
먼저 오게 되면서 글꼴 크기 기반 제목이 바뀐 슬라이드가 5장 있습니다.

애매함: 229장(8.2%, 템플릿이 반복되는 369장짜리 덱 하나를 빼면 약 6%)이 표시되며,
"자를 틈 없음" 152장, "두 방향 모두 잘림" 88장입니다. 구현한 신호는 두 방향 모두
잘림(틈 폭 2배 이내, 각 후보가 끝까지 자기 방식을 따를 때 순서가 다름)과 자를 틈
없음(텍스트 상자 둘이 나란할 때만, 그림은 제외)입니다. 부분 겹침, 경계를 넘는
컨테이너, 아슬아슬한 틈은 아직 구현하지 않았습니다.

효과가 없었던 시도: 열 우선 대신 가장 넓은 틈부터 자르기는 타임라인을 망가뜨리고
다이어그램 트랙도 여전히 실패했습니다(7/11). 틈 폭만으로는 열과 트랙을 구분할 수
없고, 그래서 이 선택은 위임합니다.

코퍼스에서 배운 점: 장식 그룹(사각형 두 개로 만든 패널)과 테두리 안의 괄호는 어느
깊이에서도 틈 계산에 참여하면 안 되며, placeholder 바로 바깥의 아주 작은 상자를
포함된 것으로 보면 안 됩니다(포함 허용치는 상자 자신의 크기에 비례).

## 계획

1. 슬라이드를 덮는 배경을 틈 계산에서 제외
2. 컨테이너 트리: 텍스트를 완전히 감싸는 테두리와 그룹을 단위로 재귀 정렬,
   정렬된 격자는 행 우선, 훨씬 넓은 틈부터 자르기
3. 애매함 신호를 순서 후보와 함께 `review()` 항목으로, 코퍼스에서 표시 비율 측정
4. 읽기 순서 레시피 규칙과, 렌더링한 슬라이드를 보고 후보 중 고르는 에이전트 단계
